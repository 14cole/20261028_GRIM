ANSWERS TO THE FOUR QUESTIONS

1. Waiting for the full cap is acceptable as a conservative interim policy.

It preserves the reservation-before-BLAS-lock ordering and avoids starting work
with a known small remainder. The cost is serialization when a solve's actual
need is much smaller than its configured maximum. Document that cost. Resolve
the effective cap from all supported sources and bound it by any stricter
scheduler allocation; the maximum a user permits is not always the amount the
worker is allowed to reserve. A later forecast-aware queue/retry is preferable
for throughput and for uncapped requests needing more than the initial guard,
but it must release failed workspaces/reservations and avoid waiting while it
holds the BLAS lock. Do not expand the current patch into an untested retry of
arbitrary numerical failures just to improve concurrency.

2. 0.5 GiB is a provisional scheduling guard, not a validated Windows minimum.

There is no Windows measurement here that establishes it as appropriate for
Windows desktops. The source comment "no 2D system fits a smaller reservation"
is false: the real concurrency fixture's H-matrix solves fit a 0.45 GiB cap.
Replace that assertion with an explanation that this is a conservative entry
guard for uncapped overlapping requests. It neither proves a larger solve fits
nor optimizes small solves. Keep physical/commit headroom gates and cancellation;
qualify the constant on Windows before making platform-wide claims. A known
forecast is a better admission criterion than a universal fixed floor.

3. Yes, the bounded retry should apply in batch and frequency workers.

Each worker makes its own outermost public call, so it can perform the same
one-retry recovery under its existing allocation. It must not enlarge that
allocation, change an explicit threshold override, or bypass backward-error
gates. I tested real spawned frequency workers with natural tile-rank rejection
and a frozen HPC worker locally; see results below. This validates those worker
paths, not an actual SLURM cluster or Windows multiprocessing.

4. Keep the bounded retry for now instead of lowering the explicit threshold.

This is the smaller behavior change: accepted tile solves remain accepted tile
solves, while previously rejected requests can recover. A global 1,024 switch
would need broader performance, memory and formulation calibration, including
exclusions and high order. Automatic already offers the lower threshold without
paying for a failed tile attempt. Keep reporting the rejected-attempt cost and
the actual backend. Future simplification can remove the retry if measurements
justify a single explicit-compressed threshold; current evidence does not prove
that is universally better.

OI-01 — MEDIUM: EFFECTIVE RAM CAP IS NOT RESOLVED AT ADMISSION

execution/options.py, outer call(), reads only:

  requested = kwargs.get('execution_options')
  wanted = requested.get('ram_budget_gib') if isinstance(requested, dict) else None

It does not consult current_options(), allocated_memory_budget(), or the launch
environment. These are supported sources used by the numerical admission gates.
The same request therefore waits or fails depending on how its cap was supplied.

probe_inherited_admission.py uses the real configured_execution public wrapper,
real memory scopes and rank_candidates, with physical capacity mocked to 1 GiB.
A peer holds 0.4 GiB; the tested request has a cap of 0.8 GiB and its candidate
needs 0.75 GiB. No large numerical arrays are allocated.

Cap source                  Waits?    Result
execution_options argument  yes       passes with 0.8 GiB after peer releases
inherited execution_scope   no        MemoryError: 0.60 GiB budget, 0.75 needed
inherited scheduler cap     no        same refusal
GHOST_MAX_SOLVE_GB           no        same refusal

All four use the same controlled cohort and candidate. This is evidence that
the fix is incomplete, not a claim of numerical field corruption. The new
0.5-GiB floor improves sliver reservations for these callers but cannot honor
their actual cap. Source lines near 809-816 are the requested correction point.

Resolve the effective validated options before entering memory_scope, with the
same precedence as invoke_configured; pass the smallest applicable positive
explicit/scheduler cap. Preserve an explicitly supplied None override according
to existing option semantics. Avoid duplicating a subtly different resolver in
call(). Add tests for direct, inherited, environment and allocation-only caps,
including a configured cap larger than the scheduler reservation.

The existing "do not wait while holding BLAS" exception remains necessary.
This response does not recommend removing it to force every caller to wait.
