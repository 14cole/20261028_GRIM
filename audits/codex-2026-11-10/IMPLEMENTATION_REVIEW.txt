1. P1 — R-1 introduces a memory/BLAS lock inversion

Location: tools/GHOST/ghost_backend/execution/memory_budget.py:420-428;
interaction with execution/options.py:481 and :502.
https://github.com/14cole/20261028_GRIM/blob/1a6addedc89c8e6f9cd52b7e5aaa098a8962dcdb/tools/GHOST/ghost_backend/execution/memory_budget.py#L420

A public solve A under execution_scope(..., limit_blas=False) reserves the
available memory. Another thread B enters execution_scope(..., limit_blas=True)
and starts a public solve. B holds _BLAS_LOCK while waiting for A's reservation
to be released. A reaches solve_fields and waits for _BLAS_LOCK. Neither can
finish. Moving the wait before locks acquired INSIDE configured_execution does
not address callers that already hold the execution-scope lock.

Reproduction: edge_checks.py lock_inversion uses actual public solves of a
68-panel PEC circle. A barrier after the first real stable() reservation fixes
the scheduling order; it does not replace reservation or locking decisions.
Both threads remain blocked: A's captured stack ends at options.py:502,
B's at memory_budget.py:428. Cancelling B releases its BLAS lock and lets A
finish. No threads remain alive after the test. With the same arrangement on
main, B raises the original zero-GiB MemoryError and A completes; it does not
deadlock. Ordinary concurrency tests passing do not cover this lock ordering.

Requested change: enforce one acquisition order across execution_scope and
public-solve reservation entry, including externally entered scopes. Do not
wait for another request while holding a lock that request needs. Add this
mixed-scope regression and test abort and exception cleanup.

Evidence: results/lock_inversion.json and results/lock_inversion_base.json.

2. P2 — R-3a still loses the sweep when a pool breaks during submit()

Location: tools/GHOST/ghost_backend/execution/frequency_sweep.py:286-287.
https://github.com/14cole/20261028_GRIM/blob/1a6addedc89c8e6f9cd52b7e5aaa098a8962dcdb/tools/GHOST/ghost_backend/execution/frequency_sweep.py#L286

BrokenProcessPool is caught around future.result(), but executor.submit() can
raise the same exception after the management thread notices worker death.
The submission site remains outside the recovery handler, so the exception
escapes compute_parallel instead of returning pending work to the parent.

Reproduction: edge_checks.py submit_death runs the real compute_parallel path.
An executor subclass kills only its own first worker with SIGKILL immediately
before the second submission and waits for the executor to observe that death.
The real superclass submit raises BrokenProcessPool at line 287. This is a
controlled scheduling reproduction, not a claim that every worker death hits
the race. Claude's supplied death-after-submission test passes independently.

Requested change: handle pool failure during submission as well as result
collection. Retain completed results, stop submitting, drain/close the broken
pool safely, and return every unfinished frequency for the sequential path.

Evidence: results/submit_death.json.

3. P2 — S-5 can publish coarse kernels outside its stated tolerance

Location: tools/GHOST/ghost_backend/bor/kernels.py:1743-1760.
https://github.com/14cole/20261028_GRIM/blob/1a6addedc89c8e6f9cd52b7e5aaa098a8962dcdb/tools/GHOST/ghost_backend/bor/kernels.py#L1743

Passing every fourth point's check does not establish that the unprobed coarse
values satisfy NEAR_ANGULAR_RTOL=2e-8. Unlike the former fine output, the new
coarse output can have a material quadrature error at unprobed points.

Minimal reproducible fixture: k=80, m_max=92, 32 point pairs in one layout.
Every fourth pair is (rho_p,z_p,rho_q,z_q)=
  (1.0140625, 0, 1.0140625, 0.1017733529476957).
The other pairs are
  (1.1390625, 0, 1.1390625, 0.11898510425967053).
Both use coarse orders [60,120]. Probed coarse/fine discrepancy is 1.179e-9,
so the chunk is accepted. At an unprobed pair the published native result is
3.21825e-7 from independent scipy.integrate.quad_vec integration of the
explicit 3-D Green function — 16.1 times the stated kernel tolerance.
The NumPy fallback has the same error. Fine mode has about 9.1e-14 error.
The pinned main implementation also has about 9.1e-14 error on this fixture.

repro_coarse_near.py reproduces this without replacing numerical functions.
The independent reference integrates exp(-ikR)/(4*pi*R)*cos(m*phi), doubled
over [0,pi], with 1e-12 absolute and relative integration tolerances. The
error uses the maximum over the point's modal values, matching the gate's
normalization, rather than division by a near-zero individual mode.

A separate smooth 257-pair grid also produced accepted unprobed errors up to
2.1624e-8 without the constructed ordering. The stronger example came from
grouping two points with the same layout after examining all points in 42
kernel cases (10,794 points). It is above the original ka<=30 calibration;
the current default has no corresponding domain restriction.

Requested change: retain fine publication outside a justified domain, or
qualify the actual published coarse values with a check/bound that covers all
points. A smaller probe discrepancy alone does not bound the unprobed ones.
Keep the fine switch and add the fixture in native and fallback modes.

Scope: this proves a kernel acceptance regression. I have NOT demonstrated a
wrong certified end-to-end RCS result from this fixture.

Evidence: repro_coarse_near.py; results/coarse_repro_latest.json;
results/coarse_repro_base.json; results/near_probe_search.json.

4. P2 — S-1/S-2 calibration silently uses higher orders than requested

Location: audits/claude-2026-11-10/calibration/w_far_rule.py:35-43.
https://github.com/14cole/20261028_GRIM/blob/1a6addedc89c8e6f9cd52b7e5aaa098a8962dcdb/audits/claude-2026-11-10/calibration/w_far_rule.py#L35

w_block patches _graded_w_far_floor and _graded_far_order, but the new
_graded_w_far_order remains active. A floor of 2 does not disable its table.
For two collinear unit panels with centers separated by 3 and k=1, calls
labeled q=5, q=6 and q=7 all actually use 7-point Gauss rules and return
bit-identical blocks. q=8 and q=48 use their requested orders.

Consequently rerunning the checked-in calibration cannot reproduce genuine
five-/six-point columns or establish the claim that one fewer point fails.
The 48-point reference and the separate assembled-matrix regression remain
useful; this is not evidence that all production table entries are inaccurate.

Requested change: bypass both W grading functions when explicitly measuring
q, assert the actual rule used, and regenerate the calibration outputs. I
independently checked 1,512 separated Maue blocks with explicitly selected
orders against 64-point integration, including low frequency and slivers;
worst error was 4.24e-14 on that different, limited grid. That positive result
does not repair the checked-in calibration helper.

Evidence: edge_checks.py calibration_orders; results/calibration_orders.json;
numerical_checks.py w_grid; results/w_grid.json.
