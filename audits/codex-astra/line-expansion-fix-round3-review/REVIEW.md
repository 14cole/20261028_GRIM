# Round-three Line Expansion review

**Hold the six-file merge.** At `d1b96fd`, newly expanded sections-only files open in the GRIM Assembly panel and the placed-feature calculation now honors their recorded attitude. The remaining release issue is what happens between saving that file and using it again. GRIM can discard a known body attitude during a crop, and Assembly can ignore a valid attitude on an edited body-of-revolution (BoR) file. Both paths silently save numerically incorrect results. [Claude’s round-three reply](https://github.com/14cole/20261028_GRIM/blob/d1b96fd5c0fe77f67de8816f9eff082c9a370644/audits/claude-2026-11-26/astra-audit-response/LINE_EXPANSION_FIX_ROUND3.md)

## Results on ordinary workflows

The reported percentages are the largest absolute complex-field difference divided by the peak magnitude of the reference field in that fixture. We reopened the files and compared the feature contribution separately from the combined field. The percentages apply to these examples.

| Workflow | Observation on round three | Control |
|---|---|---|
| Crop a rotated sections-only file to two existing azimuths, then add a point in Assembly | GRIM Crop dropped the Line Expansion record. Assembly used (0°, 0°, 0°) in place of (20°, −10°, 15°). Added-feature error was 146.13%. Combined-field error was **128.73%**. | The two cropped input looks matched the original. Using the intact base and selecting the same two looks in Assembly gave `7.66e-16` added-feature error and `6.75e-16` total error. |
| Relabel 0° as 360° on a rotated, expanded BoR file, then add a point | Every input sample was identical after reordering. The new reader still returned all three correct angles. The embedded-body branch nevertheless used its fallback zeros and saved a result whose record still identified the original nonzero attitude. Added-feature error was 156.93%. Combined-field error was **128.84%**, including when supplying a matching STL. | The intact BoR file and the edited sections-only counterpart were correct to about `1e-15`. Using the recorded orientation in the BoR plan restored the edited case to `7.92e-16` total error. The older fallback also reproduced on main and round two. |
| Change one azimuth from 45° to 50°, then exclude it from the Assembly study | All selected input values were identical to the intact control. Assembly planned at zero and gave **152.17%** total error. On the saved subset, the reader again treated (20°, −10°, 15°) as trustworthy. The validation warnings did not identify the orientation mismatch. | The same study on the intact file gave `8.27e-16` total error. |
| Regrid a rotated section in the same coordinate frame | GRIM’s interpolation path dropped the record for both an exact subset and a grid with half-degree intermediate samples. The added feature had **87.16%** and **88.39%** error respectively. Subtracting each actual regridded base isolated the feature error from interpolation of the base. | Carrying the source attitude and the resulting grid through this specific resampling operation reduced each error below `1.2e-15`. |

The missing record originates in GRIM’s derived-data handling. The BoR mismatch has a different cause: the shared reader can substitute zero angles, and the Assembly planner consults the new Line Expansion record only in its external-geometry branch. The direct `add_features_to_monostatic_grim` API can also accept an explicitly conflicting grid and carry the original record into the output. **The whole-step shift in Claude’s limitations is reproducible and repairable at edit time.** On a regular angular grid, successive Axis Edits moved every label by 60°. The final coordinate set matched the original modulo 360°. An independent section calculation at the shifted orientation reproduced the base within `3.53e-15`. The reader nevertheless trusted the old attitude. Line Expansion produced **69.02%** sum error without warning and rejected the correct stated angle. The built-in Shift command instead dropped the record and allowed a correct restatement. An exact crop and an equivalent wrap also dropped the record, even though neither changed the physical directions. Membership of coordinate sets alone cannot distinguish these operations. The operation performing the edit has both the original and resulting coordinates. [Record validity check](https://github.com/14cole/20261028_GRIM/blob/d1b96fd5c0fe77f67de8816f9eff082c9a370644/tools/GHOST/ghost_backend/assembly/fields.py#L1982) · [Axis Edit](https://github.com/14cole/20261028_GRIM/blob/d1b96fd5c0fe77f67de8816f9eff082c9a370644/GRIM_Backend/datasets/axes.py#L242)

The sections-only 0°→360° edit retained its known attitude and rejected a contradiction.
- Ordinary phase-and-power re-expansion and both previous strict Assembly controls passed. The bound sibling cancellation callback and one-shot publication cancellation kept the old destination. The successful concurrent export published its own 30° result. The native v1/v2 grid-admission replay matched round two byte for byte. The separate Windows distribution run, packaging, native diagnostics and Linux memory-admission work remain open.

## Compatibility and immediate use

For a **fresh, rotated Line Expansion file**, use the original output and select the stored angles in Assembly’s optional study subset. We tested azimuths 45° and 120° this way and recovered the reference at the errors quoted above. For the expanded BoR workflow, keep the original azimuth labels when passing the file to Assembly. [Study subset control](https://github.com/14cole/20261028_GRIM/blob/d1b96fd5c0fe77f67de8816f9eff082c9a370644/GRIM_Backend/assembly/panel.py#L2002)

Sections-only files written by the round-one or round-two trial branches still carry a BoR-style request and are refused by round-three Assembly. Expanding one again uses its known numeric orientation but adds another section. To reproduce the same result, regenerate from the original inputs. A round-two file whose angles were marked as assumptions also lost that qualification on re-expansion in round three. Released main files remain readable. For a rotated sections-only result from main, supply its known orientation when expanding it because main did not store it. Genuine unedited BoR files from all three older revisions passed the compatibility checks. A separate legacy case lacking an optional logarithmic unit remains usable for ordinary expansion but fails strict Assembly. That strict-mode behavior predates these changes.

## Bounded handoff for Claude

1. Carry a valid source attitude across operations known to preserve the physical frame, including exact crop, equivalent wrap and angular regridding in the same frame. On an edit that changes the meaning of a look, update the orientation only when justified, or invalidate it explicitly. Keep that invalidation through later subsets so the old claim cannot become authoritative merely because the edited row was omitted.
2. Resolve the effective attitude consistently in embedded and external Assembly planning and direct field addition. Compare a supplied grid with a trusted stored attitude, and ensure the saved record agrees with the calculation. When a known transformed input has lost its attitude, warn or require the value before adding features.
3. Recreate one rotated sections-only case and one rotated expanded BoR case with independent angles. Compare input samples, effective plan, added field and output metadata after actual GRIM transformations. Pass the existing 62 tests alongside the cropped, edited-BoR, excluded-row and shifted-grid cases above. No dense/compressed solver performance work is needed to decide these findings.

In disposable controls, changing **only** the transferred metadata for the known frame-preserving cases restored all added fields to within `1.2e-15`. A separate edit-side trial made the full-step shift warn and accept the correct restatement. These tests isolate the failure without proposing a blanket metadata copy for arbitrary transforms.
