# Review of the solver sessions at ed90b65

**Decision.** Keep the accepted solver and GUI changes on `main`. Use them for solver testing. The earlier advice listing only Windows and a 32 GB desktop run as remaining distribution checks was too broad. Line Expansion can crash or silently write incorrect fields in supported workflows. This changes the release advice for the full application.

## Findings that change release advice

1. **Line Expansion can silently publish incorrect complex fields.** Fifteen relevant implementation files in current main have the same Git blobs as the earlier audit. I used an actual 128-panel PEC section solver and saved and reopened the resulting `.grim` files. An imported base with physically equivalent radian axes was accepted without warning and produced a **47.22%** normalized complex-field error. Adding the same section to a base with nonzero body attitude should double the field. Implicit reuse gave **33.44%** error, and explicitly restoring the original orientation gave the expected field exactly. On a four-channel base, the addition produced a VH magnitude of 0.01342 while HV stayed zero. The line-expansion provenance record was missing after reopening. These figures are maximum absolute field differences divided by the maximum expected field amplitude for these fixtures. They are not error estimates for an ordinary standalone solver run. [Previous independent audit](https://github.com/14cole/20261028_GRIM/blob/7a5e9fdabe0e22de1fd74ef01bb4a22f07567733/audits/claude-2026-11-10/line-expansion/AUDIT_OF_CODEX_LINE_EXPANSION_AUDIT.md) · [Disposition and corrections](https://github.com/14cole/20261028_GRIM/blob/5dd8e4a01f9eb91554da7e0cd8d426ed4206f5f7/audits/codex-2026-11-11/line-expansion-response/RESPONSE_TO_CLAUDE.txt)
2. **Body shadowing can crash on a valid mesh.** A line crossing a square sheet gave the analytical visible fraction of 0.5 with two triangles. The same sheet tessellated into 648 triangles raised a tuple/list comparison `TypeError`. The earlier finding about mixing intervals from multiple leaves holds. Assembly line features use the same function. Only the shared routine was exercised directly in this check. The earlier report also covers Line Expansion cancellation, sweep input handling, fixed section solver settings and contradictory help text. These are distinct from the corrected Solver-tab Cancel button. [Visibility routine](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/ghost_backend/geometry/line_visibility.py#L118)
3. **The GHOST wheel and source tarball omit a vendored license notice.** Both freshly built packages contain `_threadpoolctl.py` without its accompanying BSD notice. The application checkout and separate source ZIP contain the notice. A trial adding `LICENSE-3.6.0.txt` to the package data for `ghost_backend.execution.thread_control` included it in all three formats. Verify the final archives before publishing wheels or sdists. [Package configuration](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/pyproject.toml) · [Vendored notice](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/ghost_backend/execution/thread_control/LICENSE-3.6.0.txt)
4. **Linux can over-admit RAM inside a nested cgroup.** The memory probe checks the mount root. Under a reproducible synthetic process/ancestor hierarchy with 1 GiB available in the relevant group, the request ledger saw 24 GiB and assigned a 21.6 GiB solve budget. Moving the same limiting group to the visible root correctly assigned 0.9 GiB. This used the production request ledger with a fake filesystem and required no large allocation. A container or systemd job with a tighter nested quota is at risk. The result is separate from the Windows and historical scale measurements. [Probe](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/ghost_backend/twod/solver.py#L1501-L1559)
5. **The speed diagnostic can report success after native acceleration is lost.** All eight shipped binaries and their four C sources matched their manifests. The Linux libraries loaded and the Windows export tables contained the required symbols. In a disposable Linux checkout, removing the 2D near library still yielded seven OK rows and exit 0. Substituting a loadable library without the far exports also yielded seven OK rows while the far/scatter/tile fast paths were unavailable. The previous positive claims about the actual shipped libraries have independent support. The stand-alone diagnostic cannot establish them. [Diagnostic](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/scripts/check_speed_paths.py#L23-L38)

## Fresh numerical and GUI checks

- I verified the contents of all 528 files in the local runtime against the GitHub main tree. Two physical fixtures exercised PEC and lossy magnetic dielectric circular cylinders at 1.35 GHz, at 96 and 512 panels, with Dense and Compressed and 180 monostatic angles per solve. Both polarizations were compared with an independently implemented cylindrical-wave solution. The worst relative complex-amplitude error fell from 0.432% to **0.0151%** on refinement. Maximum Dense/Compressed relative field 2-norm difference was **1.14e−14** or smaller. The fine dielectric case actually used the hierarchical matrix path. Repeating that case with all three 2D native libraries unavailable changed the complex fields by at most **8.06e−15** in relative 2-norm. This checks accuracy on these fixtures, including the fallback paths.
- A fresh memory/disk/disk/memory sequence exercised the shipped Dense residual-storage option at 3,584 unknowns and 180 incident angles in separate Linux processes. Peak process RSS was 0.500 GiB in both in-memory runs and 0.308 GiB in both disk runs, roughly 38% lower. All complex fields were identical and the quality gate passed. The disk runs took 16.85 and 18.05 s versus 16.95 and 17.11 s in memory. Two repeats on this filesystem give no portable speed claim. RSS excludes the filesystem cache.
- Replaying the original PR #1 four star-geometry checks plus the 4,096-unknown active cancellation and recovery check succeeded. Recomputing PR #1’s saved arrays recovered the quoted 6.91e−14 field and 4.42e−13 density differences. The fresh five-case replay gave maxima of 3.94e−15 and 2.47e−14, respectively, across the two backend pairs. The largest sampled exact-row backward error across the fresh replay was 8.17e−15. All 36 assertions in the selected original BoR, density-floor and input/warning regression scripts passed. On a separate PEC sphere (radius 0.08 m, ka 3.3, four aspects, two polarizations), native and forced fallback results agreed to 8.44e−15 relative RCS or better. Both were within 0.00965 dB of the Mie reference.
- A new GUI test exercised a **real P2-to-P3** convergence check using the untouched startup choices. Both channels published the fine result with 128 panels. All 741 progress callbacks showed the activity indicator, and the terminal value was 100. This extends the old fixed-panel test and confirms the default-policy documentation correction below. The first audit harness lookup expected per-channel polynomial orders on the aggregate record. I corrected the harness to read the channel records and reran it successfully.
- A packaged Compressed GUI solve on a 1,024-panel PEC circle at 1.1 GHz used `cpu_hmatrix`. All 360 exported complex amplitudes matched their in-memory values after reopening the file. A real click canceled during mesh checking and preserved the previous result. The restart passed. The real overwrite dialog appeared at 99%. Declining kept the existing file byte-identical, and the completed solve reached 100%. A separate GUI BoR run displayed activity through all 306 sampled in-flight observations and finished at 100%. A first multifrequency cancellation harness waited for a stage message unavailable during pool execution, so that case is counted as a completion, not a cancellation. The original 14-check harness simulated export outcomes. These new tests exercised an actual file and dialog.
- Recounting Claude's archived timing trials gave 33 canceled and 18 completed. All 51 started with Cancel enabled. Of the 12 late clicks, 11 occurred at 99% and one at 90%. Geometry menu and selection checks also reproduced. This evidence is for the Solver UI on Linux/PySide6. The supported Windows check should use the declared PySide6 environment.

## Solver settings and quality claims

A new 2D monostatic GUI job uses **Automatic** for the linear solver and **Find converged mesh automatically** for the mesh workflow. The GHOST README incorrectly says the default backend is Compressed. The delivered policy prefers Dense below 10,000 forecast unknowns and Compressed starting at 10,000, among candidates admitted by its memory policy. This is an implementation threshold, not a universal speed crossover. Use **Solve specified mesh** to skip mesh refinement on an already validated mesh. Sizing, grading, polynomial order and the requested angles still determine the actual work. A previous result's refined mesh is not automatically reused. Mesh agreement applies to the requested fields and tolerances. A pass does not validate the physical model or set a rigorous absolute field-error bound. [README](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/README.md#L36-L39) · [Run profiles](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/RUN_PROFILES.md#L3-L6) · [Actual policy](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/ghost_backend/execution/policy.py#L12-L31)

The production BoR near rule publishes the finer result by default. An originally reported 4–18% operator speed benefit applied to the optional coarse rule. In an independent calculation on the published counterexample the probed coarse/fine difference was 1.18e−9, but a different point had a coarse error of 3.22e−7 against fine periodic quadrature. Its fine-rule error was about 6e−15. The under-resolved-panel guard and the warning for a resonance-sensitive mixed Robin scene likewise qualify numerical use. Neither a small algebraic residual nor a warning resolves an inaccurate discretization. [BoR numerical scope](https://github.com/14cole/20261028_GRIM/blob/ed90b65/tools/GHOST/BOR_PERFORMANCE.md#L556-L565) · [Original detailed review](https://github.com/14cole/20261028_GRIM/blob/7a5e9fdabe0e22de1fd74ef01bb4a22f07567733/audits/claude-2026-11-10/HANDOFF_ROUND2.md)

## Handoff for Claude

1. Run an independent Line Expansion case **before** looking at the included numbers. Use two tessellations of one analytically occluding sheet, equivalent degree and radian base grids, a real four-channel base, and a chained nonzero-attitude case. Reopen the written files, check reciprocal channels and metadata, then compare numerical differences with the attached evidence. Confirm or revise severity and propose regression cases for the fixes. Revisit the remaining items in the earlier nine-item audit before recommending the full application.
2. Independently build the wheel, sdist and source ZIP in a clean directory and inspect their contents. Check missing, unloadable and loadable-but-wrong near/far binaries in a disposable checkout. Confirm which warnings are visible to an end user and whether the proposed package-data change restores the full notice.
3. For Linux RAM admission, run the included deterministic controls, then check an actual nested cgroup with a small harmless probe, including a finite ancestor and a mount rooted below the global hierarchy. Report remaining bytes and the admitted request budget. Use a root control. A deliberate OOM is unnecessary. Test a corrected implementation independently before widening deployment claims.
4. For Windows acceptance, use the actual 32 GB desktop with the intended package and a representative model. Record dimensions, materials, frequency, panel count, polynomial order, unknowns per system, incident angles, selected backend, peak working set/private commit, wall time and quality outcome. Repeat a cancellation at a recorded stage, then restart and reopen an export. Judge this separately from the Linux tests. Pending inputs are access to the machine and a representative model.

The earlier large-run timings were reanalyzed from saved data, including five hash-verified numerical archives. The multi-hour sweeps were not rerun for this review. Evidence is focused on the claims and changed paths, rather than full validation of every GRIM/FREDDY feature, every geometry, or a 32 GB capacity bound. Report fresh results and historical replays separately. A disagreement should name the commit, exact input, backend actually used, and metric.
